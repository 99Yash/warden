# OpenCode lanes — down and up lanes, materializer, driver

Slice #42 / ADR-0053 §9. The method sources are canonical; the OpenCode
agent config is generated from them; the driver (`warden opencode-review`)
is the path on which the publication rule is enforced rather than
procedural.

## Materialize and check

Each lane has a charter: `docs/reference/lanes/down.md` and
`docs/reference/lanes/up.md` (the up lane is off by default; see
[The up lane](#the-up-lane-default-off)). A charter holds only what no
existing method doc says (the lane's job, the mandatory protocol, the
submission contract) plus a fenced `includes` list naming the method
sections the materializer splices in verbatim. Material that only one
lane needs lives under `docs/reference/lanes/` (for example
`exemplars.md`, which only the up lane includes), so each lane loads only
the sections its charter selects.

```
pnpm lanes:materialize   # regenerate packages/cli/opencode/*
pnpm lanes:check         # regenerate in memory, exit 1 on drift
pnpm --filter @warden/cli lanes:measure   # offline prompt size report
```

`lanes:check` compares regenerated bytes against the committed files and
names each drifted file. Any method-source edit requires re-running
`lanes:materialize` and committing the result. The materializer
(`packages/cli/src/opencode/materialize.ts`) is pure — inputs are file
contents, outputs are file contents — with the script entry at
`packages/cli/scripts/materialize-lanes.mts`. Section extraction matches
headings exactly (a missing heading throws naming the file and heading)
and strips single-line `<!-- … -->` comment lines.

### The lane spec

A **lane spec** (`LaneSpec` in `materialize.ts`) is the data for one
lane. The materializer and the driver take it as an argument, so a new
lane is a new spec and a new charter, not new code. `LANE_SPECS` lists
the lanes that `lanes:materialize` writes: `DOWN_LANE_SPEC` and
`UP_LANE_SPEC`.

| Field | What it controls |
| --- | --- |
| `lane` | The post-pass lane name in the lane envelope and the `lane-trace` entry. |
| `agentId` | The agent key in the config and the `--agent` value. |
| `tier`, `defaultModel` | The `--model` value when the operator gives none. |
| `steps` | The agent step cap. |
| `scopeBudget` | The charter's step cost: steps for each changed file, and the fixed steps. The scope ceiling is `floor((steps - 2 - fixed) / stepsPerFile)`. |
| `description`, `allowedTools` | The agent description and the read-only tool allows. |
| `charterPath` | The canonical charter. Its fenced `includes` list names the method sections. |
| `promptFilename`, `configFilename` | The two generated files. Each lane has its own config, because `compaction` is a top-level key and one private `serve` reads one config. |
| `requiredPhrases` | Phrases the prompt must keep: the read/grep exclusions and the read bound. `lanes:materialize` and `lanes:check` fail when one is missing. |

These parts are the same for every lane, so they are not spec fields:
the permission list (deny first, the secret guard, the Git-metadata
deny, the two warden MCP tools), `codemode: false`,
`compaction: {auto: false}`, the finding schema at the end of the
prompt, the gates before spawn, and the submission contract below.

`smoke:opencode-lanes` pins the sha256 of the down lane's two generated
files. `lanes:check` compares the generated bytes with the committed
files, so a materializer change that regenerates both would pass it. The
pinned hash does not move. A deliberate change to the down charter or to
one of its included sections updates the two hashes in the same commit.

## Generated files

`packages/cli/opencode/` holds two committed files per lane (shipped with
the CLI build — tsdown copies the directory to `dist/opencode/`, and the
driver resolves it relative to its own module in dev and dist). The down
lane's files are below. The up lane has the same shape in `warden-up.md`
and `opencode-up.json` (`agents["warden-up"]`).

- `warden-down.md` — the assembled system prompt: generated banner, the
  charter body, each included section verbatim, then the finding JSON
  schema rendered from `z.toJSONSchema(LaneFindingSchema)` (imported from
  `@warden/core`), so the schema in the prompt cannot drift from the
  post-pass.
- `opencode.json` — v2 agent config: `agents["warden-down"]` with
  `mode: "primary"`, the strong-tier default model, `steps: 60`,
  `system: "{file:./warden-down.md}"` (substituted relative to the config
  file's directory), the permission list below, and
  `mcp.servers.warden = {type: "local", command: ["warden", "mcp"],
  codemode: false}` (the driver re-states the full server object per install
  via `OPENCODE_CONFIG_CONTENT` — the host resolves config per top-level
  key, so a partial override would replace the whole `mcp` key and drop
  `type`/`codemode`), and the top-level `compaction: {auto: false}` (see
  [Compaction is off](#compaction-is-off)).

## Permission list

First rule denies every tool; later rules allow only read-only tools and
the two warden MCP tools. Order matters — the last matching rule wins, and
agent rules are appended after global rules so they win:

| Rule | Why |
| --- | --- |
| deny `*` / `*` | Closed by default; a `deny *` also removes the tool from the model's view. |
| allow `read` | Read changed files and their context. |
| deny `read` on `*.env`, `*.env.*` | Secret guard (mirrors the built-in `explore` agent): agent rules append after global rules and the last match wins, so a bare `allow read *` would re-open `.env` files the host default and the user's global config deny. Deny, not ask — the host enforces a deny before any client reply, while an ask depends on the run client's reply, which is version-dependent. Residuals: the `read` deny is the only enforceable guard — no ruleset can path-restrict `grep`, because the host keys grep permission on the search pattern and passes `path` / `include` as un-matched `metadata` (`packages/core/src/tool/plugin/grep.ts:87-99`, `packages/core/src/permission.ts:87-92`; see the ADR-0053 slice #42 amendment), so a `grep` deny rule would be a placebo; `.ENV` case on case-insensitive APFS; a committed symlink to `.env` (followed after a link-path-only check, verified live 2026-10-14 — the diff symlink gate in ADR-0054 §2(g) is the control); and `*.env.*` also blocks names such as `src/config.env.ts`. |
| allow `read` on env templates ending in `.example` or `.sample` | Templates such as `.env.sample` and `.env.local.example` stay readable. Credential-format checks still apply to publication. |
| deny `read` on credential files | `READ_SECRET_FILE_GLOBS` also covers `.npmrc`, `.netrc`, `.dev.vars`, `.envrc`, private-key names, key/certificate bundles, and `.aws/credentials`. Git metadata denies apply after template exceptions. |
| allow `grep` | Find the one-hop caller or definition site of a changed symbol (the `grepRepo` role in method docs). A grep hit does not count against the per-claim file bound (see the submission contract). |
| allow `glob` | Locate files by pattern. |
| allow `warden_run_det_priors` | Phase-1 ground truth; the driver fails the lane on zero completed calls. |
| allow `warden_lookup_type_def` | Verify library-API claims before asserting them. |

No `shell` (`git diff --output=` can write, so shell stays denied — the
diff arrives through `warden_run_det_priors`), no `edit` (the lane never
writes), no `webfetch`/`websearch` (claims must be repo- or `.d.ts`
grounded), no `subagent` (one agent-sized unit of work), no `*` allow.
Without `--auto`, the run client rejects an ask and tells the model to
continue without the action — the action does not run, and the lane
continues (verified against the shipped binary v2.0.25; the `v2` source
checkout interrupts the session instead — trust the binary). So the
driver never passes `--auto`: `--auto` replies `once` (allow).

## Read/grep output bounds (issue #57)

The host bounds each call but no config tightens it, so the charter's
read/grep scope rule (`down.md` protocol step 2) is the only lever.
Verified at commit `b1e3a7b222` and in the shipped binary v2.0.25:

- `read` pages at 2,000 lines / 50 KiB, lines cut at 2,000 chars —
  hard-coded (`packages/core/src/tool/read-filesystem.ts:14-18`, `:283-305`).
- `grep` returns 100 matching lines by default, each cut at 2,000 chars
  (`packages/core/src/filesystem.ts:34`, `packages/core/src/ripgrep.ts:255`);
  the model-supplied `limit` has no upper bound (`filesystem.ts:47`).
- The configurable `tool_output.max_lines` / `max_bytes` truncation skips
  any result that already sets `metadata.truncated`
  (`packages/core/src/tool-output.ts:66`), and `read` and `grep` always set
  it (`tool/plugin/read.ts:117`, `tool/plugin/grep.ts:152`). Setting
  `tool_output` in `opencode.json` does not bound either tool.

Context is re-sent every turn, so even bounded calls compound: a 50 KiB
page of `decisions.md` or a fixture `diff.patch` costs its tokens on every
later turn.

## Compaction is off

A review lane must not compact. Compaction replaces the older turns with
a model-written summary. A lane finding cites the code that the lane
read, and a summary does not keep that code. So the lane config sets the
top-level `compaction: {auto: false}`.

Facts from the shipped binary v2.0.32 (the strings, and a loopback
Anthropic stub that costs $0):

- The config key is top-level `compaction` (`Config.Compaction`: `auto`,
  `keep.tokens`, `buffer`). No agent field exists, so the key applies to
  every session on the driver's private `serve`. The default is
  `{auto: true, keep: 15000}`.
- OpenCode compacts at two points: before a step when the context is near
  the model limit (reason `auto`), and after a provider rejects a request
  as too long (reason `overflow`). With `auto: false`, both return
  `skipped`. Only a manual compact still runs, and the driver never sends
  one.
- Without the key, the stub showed one compaction before the second step
  (199,000 of 200,000 input tokens) and one after a 400 "prompt is too
  long". With the key, the stub showed none.
- The CI pin v2.0.25 (`warden-review.yml`) has the same key, default,
  `skipped` check, overflow patterns, and run-client event set. This is
  from its strings only; the stub check ran on v2.0.32.

**At the context limit.** The provider rejects the request. The run
client then writes this event and exits 1:

```json
{"type":"error","error":{"type":"provider.invalid-request","message":"prompt is too long: …","status":400,"response":{"body":"…"}}}
```

`provider.invalid-request` is the class of every invalid request. So the
driver applies the binary's own context-overflow patterns to the message
and the response body (`isContextOverflowError`). When one matches, the
lane fails with the reason `context_limit: the lane reached the model
context limit, and auto-compaction is off (<provider message>)`. This
check runs before the exit-code check, so the reason does not become
only `opencode run exited 1`. The lane-health entry is actionable, so
the result is not clean.

**Compaction count.** The `--format json` stream has no compaction
event. The run client writes only `step_start`, `text`, `reasoning`,
`tool_use`, `step_finish`, and `error`. So the driver reads
`GET /api/session/<id>/message?type=compaction` from the serve API
before it stops `serve` (`parseSessionCompactions`). The count includes
completed and failed compactions.

- The `lane-trace` entry ends with `· compactions <n>`, or
  `· compactions unknown` when the read fails.
- `DriveLaneResult.compactions` and the `--timings-out` record carry the
  count.
- A count above 0 fails a lane that is otherwise `ok`, with the reason
  `compaction: the lane session compacted <n> times, …`. The findings
  still go to the post-pass, but the result is not clean. A count above 0
  means that the binary did not apply the config key.

**How to check.** For an eval run, every OpenCode sample must have
`compactions 0` in its `lane-trace` entry, and no lane reason may start
with `compaction:`. `smoke:opencode-lanes` checks the config key, the
`context_limit` reason, the count parser, and the failed lane for a count
above 0. After an OpenCode upgrade, repeat the stub check against the new
binary.

## Model tier and `--model`

The lane is strong-tier; the default is `anthropic/claude-opus-5-5#high`
(ADR-0006 tier intent — the client's provider config owns the real
choice). `opencode run` never applies `agent.model`; it uses `--model` or
the config default — so the driver always passes `--model`
(`--model` flag overrides the default). `--agent warden-down` selects the
agent regardless of its `primary` mode.

## `codemode: false`

MCP servers default to `codemode: true`, which hides their tools inside one
`execute` tool. The warden server sets `codemode: false` so
`warden_run_det_priors` / `warden_lookup_type_def` appear as their own
tools with their own permission actions — the permission list above and
the driver's zero-call gate both depend on those exact names
(`<server>_<tool>`).

## The MCP startup race (operator amendment 2026-10-08)

The shipped binaries (v2.0.24, v2.0.25) do not wait for MCP servers
before the session tool snapshot: `SessionContext.select` awaits only the
plugin flush, not the MCP flush, and `MCP.tools()` returns connected tools
at once without a readiness wait (OpenCode source: the `mcp.tools.changed`
debounces in `state.ts:42`, the per-step tool snapshot in
`session/runner/llm.ts:164`; verified against the shipped binary v2.0.25 —
the `v2` source checkout still has both waits, so the source does not
match the binary here — trust the binary). A server that connects late fires `mcp.tools.changed` and its
tools register after short debounces, so only a later step or a later run
on a warm server sees them. Warden's MCP server (tsx) connects ~2.7–3 s
after the server starts, after the first snapshot — so a cold
`opencode run --standalone` never shows `warden_run_det_priors`. Proof:
replay MCP servers with warden's exact `tools/list` are visible when they
connect fast and missing with a 2.5 s connect delay (probes p6/p7); on one
`opencode serve`, the cold run misses the tools and the warm run shows
`warden_run_det_priors` and `warden_lookup_type_def` as direct tools
(p11/p12, real warden config).

## Serve → poll → run

The driver never uses `run --standalone`. Instead:

1. Spawn `opencode serve --hostname 127.0.0.1 --port <free port>` (flags
   verified against `opencode serve --help`: `--hostname`, `--port`) with
   the driver-owned config env (`OPENCODE_CONFIG`, both project-disable
   flags set to `1`, the isolated config and discovery-home paths,
   `OPENCODE_CONFIG_CONTENT`) plus a
   random `OPENCODE_PASSWORD`. The port comes from the OS (listen on port
   0, read the port, close). The serve child reads the env password for
   its API auth (`server-process.ts`: `Env.password`, else a random
   fallback the run client could never know); the run client sends it back
   as Basic `opencode:<password>` (`server-connection.ts`), so both
   children share it and it never leaves loopback.
2. Poll `GET http://127.0.0.1:<port>/api/mcp` with Basic auth
   `opencode:<password>`. This call also boots the location. The query is
   `location[directory]=<repoRoot>` (deepObject `LocationQuery` —
   `packages/protocol/src/groups/location.ts`; a bare `?directory=` is
   ignored by the binary and answers with the serve cwd, verified live).
   The response shape is `{location:{…},
   data:[{name,status:{status,error?}}]}` (`Location.response` in
   `packages/server/src/location.ts`, `Mcp.Server` in
   `packages/schema/src/mcp.ts`) — the driver validates it as untrusted
   JSON. Wait until the **warden** server shows `connected`; other servers
   are ignored. A `failed` warden, or no
   `connected` within 30 s (default, `--mcp-timeout` overrides), fails the
   lane with a reason naming the MCP status — `run` is never spawned.
3. Wait ~1 s more (`MCP_SETTLE_MS`) for the `mcp.tools.changed`
   debounces before the first snapshot.
4. Spawn `opencode run --server http://127.0.0.1:<port> --agent
   warden-down --model <m> --format json <message>` (flag verified against
   `opencode run --help`: `--server`; `--standalone` stays off) with stdin
   ignored. `OPENCODE_PASSWORD` stays in its env for the `--server` auth.
5. The serve child is killed on every exit path (SIGTERM, then SIGKILL
   after a grace period): success, failure, timeout, and thrown errors. A
   leaked `opencode serve` is a bug.
6. Diagnostics: a bounded ~2 KB stderr tail of both processes. A run
   failure reason carries the run tail (e.g. `opencode run exited 1
   (stderr: …)`); an MCP-warmup failure reason carries the serve tail. A
   failed lane always says why.

Both children get `PWD=<repoRoot>`. OpenCode resolves its location from
`PWD`, not from the process cwd. Under `pnpm --filter @warden/cli`, `PWD` is
`packages/cli`, so without this `run` opens a second, cold location: the
warm-up in step 2 does not apply to it, the MCP race comes back, and the
model reviews the wrong directory. The operator found this on 2026-10-08:
the same tracer passed by hand from the repo root and failed through
`pnpm warden`. `smoke:opencode-lanes` asserts that `PWD` matches the cwd.

## Project and global config lockout

The driver spawns `opencode serve` with
`OPENCODE_CONFIG=<absolute opencode.json>` and
both `OPENCODE_DISABLE_PROJECT_CONFIG=1` and
`OPENCODE_CONFIG_PROJECT_DISABLE=1`. These override inherited values;
the newer name wins in the binary. The reviewed tree cannot re-grant
permissions, add plugins, or override the agent.

Both children also get `OPENCODE_CONFIG_DIR` and `OPENCODE_TEST_HOME`
pointing to separate empty directories under a private temporary root.
The config directory excludes global config, plugins, and `AGENTS.md`.
The discovery-home override excludes home skills, including
`~/.claude/skills`; the config directory alone does not exclude them.
Provider credentials and the normal data path for saved auth remain
available. The driver removes the temporary root after the server stops,
including failure paths. `smoke:opencode-config-isolation` checks these
paths with the installed binary and a loopback model stub. This is config
discovery isolation; files and the session store remain accessible.

Residual: project `AGENTS.md` intent
context is also disabled on the driven path (there is no per-agent
opt-out), so the lane reviews without the repo's contributor guidance —
acceptable for a correctness lane, which needs the code, not the customs.

## Untrusted input (ADR-0054)

The lane reads untrusted text through tools: the diff, the files, and the
`warden mcp` output. The main attacker supplies third-party text inside a
trusted PR, such as a vendored file, a dependency update, pasted code, or a
fetched document. The
main goal is to suppress findings and obtain a clean result. Runner secrets
are a separate asset: process environment values, `.git/config`, and files
written by earlier CI steps. Same-repo-only CI does not remove this attacker;
an author who can execute a changed workflow is outside Warden's boundary.

Warden does not own the OpenCode tool output. These controls have separate
limits:

- **Independent integrity signals.** `runInputIntegrity` checks all added
  diff lines for hidden Unicode (`hidden-unicode`) and commands aimed at an
  AI reviewer or its instructions (`reviewer-instruction`). The post-pass
  publishes these as Tier 1 / `security` tool findings, even when the lane
  submits `[]` or fails. They bypass lane scope, noise pruning, and volume
  caps. `warden check`, the MCP det-prior bundle, and the legacy review
  harness also include them. Messages give code points or a rule, without
  quoting the payload. Valid language, emoji, documentation, and test text
  can match; check the text's purpose. These rules cover some suppression
  attacks. Other wording, encodings, unchanged text, and fetched documents
  can evade them. A clean result does not prove the absence of injection.
- **Nested `AGENTS.md` gate.** After each `read`, OpenCode loads each
  `AGENTS.md` between the file and the location root as session
  instructions. No flag stops it (binary v2.0.25: `uL="AGENTS.md"`,
  `u.up({targets:[uL],…})`). The project-config lockout above covers only
  the root file. So if the diff adds, changes, or renames to an
  `AGENTS.md` below the root, the driver fails the lane before spawn
  (`laneInstructionFileGate`, known $0, not clean). It reads the diff
  headers, because a pure rename or a binary file has no `+++` line. A
  nested `AGENTS.md` that the PR does not touch is base-branch content
  and loads as usual. Its contents can still contain hostile instructions.
- **Symlink gate and Git-metadata deny (ADR-0054 §2(g)).** The binary's
  `read` checks permission on the link path, then follows the link:
  verified live on 2026-10-14 (v2.0.25) — a committed `src/x` pointing
  outside the repo returned the outside file, and `src/gc` →
  `../.git/config` returned the config, while a direct `.git/config`
  read was denied. So the driver also gates the diff before spawn
  (`laneSymlinkGate`): a changed symlink (mode 120000, pure renames
  checked against the live checkout) whose canonical target leaves the
  repo or enters `.git` fails the lane closed, as does a declared
  symlink missing or replaced in the checkout. The lane config denies
  `read` on `.git/*` and `*/.git/*`, and the secret guard drops a
  finding that cites `.git/config` even when the credential is
  base64-encoded. A symlink already on the base branch is outside the
  diff gate and remains readable through its link path; `grep` through
  a symlink is unverified. In CI (#48), every `actions/checkout` sets
  `persist-credentials: false` so `.git/config` holds no token.
- **Base ref.** CLI `--base` and model-chosen MCP bases must be plain ref names (`assertPlainBaseRef` in core `resolveDiff`):
  no leading `-`, no `..`, no quotes, spaces, or braces. It goes into the
  lane message and into git argv. Git revision probes and diff argv use `--end-of-options`.
- **Repo-controlled detector code.** ESLint config and repo-local compiler
  executables can run arbitrary code. The MCP command starts with
  `/usr/bin/env -i` and a fixed execution-settings allowlist. Direct
  `warden mcp` sessions apply that limit and disable Warden env-file loading.
  All detector children also use the allowlist, including explicit caller
  envs. Provider keys, CI tokens, custom secrets, config paths, and Node
  startup hooks are excluded. OpenCode keeps the credentials its model needs.
  This does not isolate files or other same-user processes. For #48, run
  det-priors with no secrets; keep credentials outside resources that detector
  code can access. Fork and hosted review still need runner isolation.
- **Secret guard, defence in depth.** The post-pass drops a finding that
  cites a sensitive file (`SECRET_FILE_GLOBS` in `@warden/core`, matched case-insensitively) or holds a known credential format. The read-deny policy is separate (`READ_SECRET_FILE_GLOBS`); publication covers all read-denied paths plus credential JSON files and `.ssh/*`. PGP private-key headers, Slack app tokens and webhooks, GitLab and Hugging Face tokens, Stripe webhook secrets, URL credentials, Basic authorization, and Cloudflare token assignments/headers are included.
  It adds one `actionable` `secret-guard` entry with the rule and the
  anchor only when it is in the driver-owned lane scope and has no credential
  match. An out-of-scope file becomes "an out-of-scope anchor"; the entry
  never copies its text or the matched value. `--lanes-out` writes such a finding as
  `{ "secretGuard": "<rule>" }`. On replay, the post-pass restores the
  actionable `secret-guard` entry with the lane and rule ID. The marker
  has no anchor, so the restored entry has none. Unknown rule IDs or extra
  fields fail validation. This is DLP for accidental disclosure into
  stored output, not containment of an injected model. Arbitrary base64 outside Basic authorization headers, tokens split across fields, spaced tokens,
  plain passwords, and secret files reached through a symlink with a
  non-`.env` name can pass (the publication guard sees the link path;
  the §2(g) diff gate is what blocks adding such a link). Fixed lane
  configuration does not isolate runner secrets; runner isolation needs a
  separate design. The model provider and OpenCode session store still
  see what the lane reads.

- **Independent secret-diff findings.** The driver-owned diff is scanned for credential formats on added lines. Fixed tool findings give the rule and file/line, without values or snippets. A sensitive-file path produces a separate finding; the name alone does not prove that credentials are present. Empty additions, pure renames, and binary changes use a `0:0` file-level anchor rather than a line that does not exist. Credential-bearing filenames are omitted. These Tier 1 security findings survive empty/failed lanes, noise pruning, volume caps, and replay with the same diff. The lane output guard still drops unsafe model findings. Templates remain subject to credential-format checks.
- **Instruction filename aliases.** The diff gate decodes Git C/octal UTF-8 paths, then uppercases the basename. This catches `AGENTſ.md` on APFS in both default Git output and `core.quotePath=false`. It is not a complete filesystem equivalence check.

`smoke:secret-diff` covers credential findings and replay;
`probe:instruction-tree` is the S7 investigation described in [probe results](probes/s7-temporary-tree.md).

`smoke:input-integrity` covers detection and publication outside lane discretion;
`smoke:untrusted-input` covers the guard and authority checks;
`smoke:opencode-lanes` covers the gate, the `--lanes-out` placeholder, and replay
end to end. `smoke:secret-isolation` runs repo-controlled ESLint and compiler
code through real MCP and checks inherited and env-file secrets.

## Submission contract

The final assistant message ends with exactly one fenced ` ```json `
block holding `{"findings":[...]}`; `[]` means the lane reports no findings.
The independent integrity signals can still make the final result non-clean.
The driver takes the final message to be the `messageID` of the last
`step_start` event, and a stream with no trustworthy identity (a `text`
part without a `messageID`, a `step_start` without one, a `text` part no
`step_start` announced, or no `step_start` at all) fails the lane closed.
Each finding validates against the schema in the prompt (no `id` — the
post-pass mints it), needs ≥1 source whose `path` is a changed file with
verbatim `path`/`line`/`snippet`, pairs any `node_modules/` authority
source with an in-scope companion, uses `kind: "question"` below 0.7
confidence, and reports only **broken** and high-risk **unproven** down
conclusions.

Investigation is bounded (issue #57). The lane reads each changed file
whole, then traces each claim one hop from a changed symbol and opens at
most 3 files for it: the changed file, one caller-side file, and one
definition-side file. A claim that reaches the bound concludes
**unproven**, with the next unopened file as its missing evidence. The
included method sections ask the model to trace every symbol and to spend
the whole step cap; the charter states that the bound wins over them.
The bound phrases are in `DOWN_LANE_SPEC.requiredPhrases`, so
`lanes:check` and `smoke:opencode-lanes` fail if the materialized prompt
loses the bound.

Residual: det-prior findings are not published on the driven path — they
belong to the surface lane, which is not shipped yet, and the charter
tells the down lane not to restate them.

## The up lane (default off)

The up lane is the ADR-0052 Lever D structural pass: an up-direction
search for drift between the code's structure and the domain's
structure. ADR-0052 is proposed, not ratified, so the up lane is **off
by default**. Nothing runs it unless an operator asks for it:

```
warden opencode-review --lane up [--base <ref>] …
pnpm --filter @warden/cli eval --config opencode-up --fixture <name> --samples 1 --max-cost <usd>
```

`--lane` accepts `down` (the default) and `up`. An unknown value fails
before any spawn. The CI tracer workflow does not pass `--lane`, so it
runs only the down lane. The `opencode-up` eval config is outside
`ALL_CONFIGS`, so a bare `pnpm eval` does not run it.

Option A (the user's choice, 2026-10-20): the down lane keeps its read
cap, and the up lane has its own charter, spec, and bound. The up lane
reads the same tools under the same permission list, gates, and
submission contract. What differs is the charter:

- **Two passes.** Pass 1 reads each changed file whole and uses `grep`
  to count the homes of each changed fact. Pass 2 confirms **at most 3
  candidates**, and opens **at most 3 home files per candidate** beyond
  the changed files. A candidate that the bound leaves unproven posts
  only as a question, and only when it names the change it de-risks.
- **Admission gates.** A finding states gate A (the named change), gate
  B (the shared truth), and gate C (the enforcement tier and the
  remaining gap). Confidence reaches 0.7 only when the fix reaches tier
  1–3 of the enforcement ladder, so the post-pass demotes a tier 4–5
  closure to a question.
- **Output.** `category` is `dedup` for the repetition axis and
  `clarity` for the other axes; `tier` is 2. The anchor is an added line
  in a changed file. Other homes can be cited as extra sources, because
  `commentInScope` needs only one in-scope source and `verifyCitations`
  checks each snippet against the file on disk.
- **Included material.** Selected sections of
  `docs/reference/structural-review.md`, the exemplars in
  `docs/reference/lanes/exemplars.md`, and section 1 of
  `docs/code-style.md`. The down lane loads none of these except "Three
  review motions".

Residuals: the up lane runs alone, not next to the down lane in one
review. A combined run (both lanes into one post-pass) is a later
change. The down charter still says that the up lane "does not exist
yet"; that sentence changes the down prompt bytes, so it changes only
when the up lane goes default-on. The ADR-0052 Pass 1 axis-tagged tell
collector in `runDetPriors()` is not built, so the lane finds most of its
tells with `grep`.

## Driver flags and exit codes

```
warden opencode-review [--lane <down|up>] [--base <ref>]
  [--model <provider/model#variant>]
  [--json] [--verbose] [--volume-cap <n>] [--lanes-out <path>]
  [--timings-out <path>] [--timeout <seconds>] [--mcp-timeout <seconds>]
```

- `--lane` selects the lane spec (default `down`; see
  [The up lane](#the-up-lane-default-off)). Every item below applies to
  the selected lane.

- Resolves the diff exactly like `warden post-pass` (`resolveDiff`,
  mode `review`) and forwards its degraded entries; the scope envelope is
  `deriveLaneScope(diff)` — the same prune derivation the post-pass
  anchors against.
- Empty scope never spawns OpenCode: the lane is `failed` with
  `empty review target` so the fail-closed entries fire.
- A scope above the lane's ceiling (`laneScopeCeiling(spec)`: 58 files
  for the down lane, `DOWN_LANE_MAX_SCOPE_FILES`, and 24 files for the
  up lane) never spawns
  OpenCode either (issue #57): the lane is `failed` with a
  `review target too large: …` reason that names the file count, the
  ceiling, and its source, and `runSpawned` is `false` (a known $0). The
  ceiling comes from the lane spec's `steps` and `scopeBudget`: OpenCode
  forces a text-only step
  at `step >= steps` (the step counter starts at 1, so 59 steps can call
  tools), and the first goes to `warden_run_det_priors`. The down lane
  needs at least one whole-file read for each changed file
  (`60 - 2 = 58`). The up lane needs a read and a `grep` for each
  changed file in pass 1, plus 9 pass 2 reads (3 candidates × 3 home
  files): `floor((60 - 2 - 9) / 2) = 24`. It assumes one tool call per step,
  the rate in the recorded down-lane streams. It is not a hard limit: a
  model can batch reads (recorded up to 4 in one step). The timeout is
  not in the formula because its rate depends on the model.
- Warms its own `opencode serve` (free loopback port, random password),
  waits for the warden MCP server to connect (default 30 s,
  `--mcp-timeout`), settles 1 s, then runs against it; the serve child is
  killed on every path.
- Lane `failed` reasons are specific: MCP not ready (never connects,
  failed status, poll rejected), non-zero exit (with the stderr tail),
  timeout (default 900 s, child killed), `context_limit` (a provider
  context-overflow error; see [Compaction is off](#compaction-is-off)),
  error event, `text` part without
  a `messageID`, `step_start` without a `messageID`, `text` from a message
  with no `step_start` (final message identity unknown), no `step_start`
  in the event stream, no fenced block, multiple fenced json submissions,
  invalid JSON, no `findings` array, zero completed
  `warden_run_det_priors` calls, or a session compaction count above 0.
  Only the zero-det-priors and compaction failures forward parsed
  findings — the timeout, context-limit, non-zero exit, and error-event
  paths fail before parsing and forward `findings: []`. `--lanes-out` writes the
  envelope for audit / replay through `warden post-pass`.
- Output matches `warden post-pass` exactly; exit 1 when
  `isNotClean(result)` (actionable `lane-health` / `diff-source` / `secret-guard`).
  A guard drop causes exit 1 even when other findings publish.
- An extra `info` entry, topic `lane-trace`, records the tool-call counts
  (e.g. `warden_run_det_priors×2, warden_lookup_type_def×0, read×7`).
  After the run resolves and before the serve child is killed, the driver
  reads the session total (`GET /api/session/<id>`, same auth and
  `location[directory]` query as the MCP poll); when known, the
  `lane-trace` entry gains a `· cost $<4dp> · tokens <in>/<out>` suffix
  (`in` = input + cache reads + cache writes). A failed read leaves the
  entry as it was — usage is telemetry and never fails the lane. On a
  spawned run, the entry then ends with `· compactions <n>` (or
  `unknown`), from the same serve read phase. The
  MCP-warmup failure, empty-scope, and scope-over-ceiling paths have no
  run and no usage.
- `--timings-out <path>` writes the phase timings as JSON:
  `{version: 1, timings, runSpawned, model, usage?, compactions?}`. The driver
  records the wall-clock time of each phase that runs: `resolveDiff`,
  `gates`, `mcpReady` (this includes the serve boot), `settle`, `lane`,
  `usage` (the session usage and compaction reads), and `postPass`. A phase that does not run has no entry.
  `timings.tools` gives the completed calls for each tool and their sum
  of `state.time.end - state.time.start`. The v2.0.25 binary sets these
  two values on each completed `tool_use` part. The start is the time
  when the model starts to write the tool input, so the sum also includes
  the time to write the arguments. Phase 1 runs in the first
  `warden_run_det_priors` call. `totalMs` stops at the end of the
  post-pass, so it does not include the serve shutdown. The timings are
  telemetry: they never change the verdict.

## CI tracer workflow (issue #48)

`.github/workflows/warden-review.yml` runs `warden opencode-review` on a
pull request and records the time of each step. It is a tracer, not the
#48 runner:

- It runs only for a same-repo PR that has the `warden-review` label.
  Each run spends model credit, so the label is an opt-in.
- It checks out the PR head with `fetch-depth: 0` and
  `persist-credentials: false` (ADR-0054 §Ripple). It never uses
  `pull_request_target`.
- It installs the pinned OpenCode version (`OPENCODE_VERSION`) and stops
  if `opencode --version` shows a different version.
- Only the review step gets the `ANTHROPIC_API_KEY` and
  `ANTHROPIC_BASE_URL` secrets. The `WARDEN_LANE_MODEL` repository
  variable can change the lane model.
- The job summary shows the job step times, the driver phases, the tool
  time in the lane, the session cost, the findings, and the degraded
  entries. The artifact holds the `CommentSet`, the `--lanes-out`
  envelope, and the timings. The review stderr goes only to the masked
  job log.
- The job passes on each review verdict. It posts nothing to the PR.

These #48 items are still open: the index cache (#45), a hard cost
limit, and a PR review with the `CommentSet`.
